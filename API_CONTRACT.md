# Functional contract

Base `/api/v1`. JSON uses decimal strings for all paise and UUID strings for entity IDs. Currency INR only. Positive balance means owed to participant. Actor identity is Django/allauth session ownership. Native auth uses allauth app session tokens in `X-Session-Token`; no custom JWT/user store.

All mutating ledger requests contain `command_id` UUID. Updates also contain `version` integer. Replaying identical actor/command/payload returns the original result; changed payload returns409. Error JSON has `error` and `detail`.

- GET `/health`, `/ready` are unauthenticated liveness/database readiness.
- POST `/groups` body `{command_id, id, name, participants:[{id,name,email?}]}`. Creator is participant with their user ID linked explicitly by server. Client supplies their participant `id` as `self_participant_id`. Returns `{id:group_id,version}`; fetch snapshot separately.
- Optional `is_direct:true` creates a friend ledger with exactly two participants; adding a third is rejected. The default is false. Group lists, snapshots and JSON exports preserve the flag. Omitted and explicit false retain legacy command-replay compatibility.
- GET `/groups` returns `{groups:[{id,name,version}]}`.
- GET `/groups/{id}` returns `{id,name,version,participants:[{id,name,user_id}],expenses:[...],settlements:[...],balances:{participant_id:paise},transfers:[{sender,recipient,amount}],activity:[...]}`. The complete authorized index supplies versions. Refresh reuses complete same-version snapshots for this account/backend and fetches only missing or changed groups before reconciling access. The updated client requests bounded summaries and history pages. The legacy full snapshot remains available for older clients, exports and explicit recovery; bounded data is stored separately and never presented as a complete history.
- POST `/groups/{id}/expenses` body `{command_id,id,description,total,paid:{id:paise},split:{mode:'equal'|'exact'|'percent'|'shares',values:{id:decimal_string}},date:'YYYY-MM-DD',category,notes}`. Equal values are selected participant IDs with value'1'. Percent values total100.00; shares max4decimal places. Returns `{id:group_id,version}`; fetch snapshot separately.
- PUT `/groups/{id}/expenses/{id}` same body plus `version` of expense. DELETE body `{command_id,version}`; POST `/restore` body `{command_id,version}`. Expense output includes `id,version,description,total,paid,shares,split,date,category,notes,deleted`.
- POST `/groups/{id}/settlements` body `{command_id,id,sender,recipient,amount,attempt_id?}` creates explicit manual bookkeeping. POST `/settlements/{id}/reverse` body `{command_id}`.
- POST `/groups/{id}/opening-balances` body `{command_id,id,balances:{id:paise},source,cutoff}` creates a pending balanced opening proposal. It posts only after every nonzero linked participant acknowledges.
- GET `/groups/{id}/export?format=json|csv` returns accepted records with allocations and provenance.

Payment attempts, invites/claiming, account export/deletion and group archive have the explicit endpoints below. The mobile client uses plain fetch and persists queued commands; no generated SDK or generic command bus. The Python API is authoritative; TypeScript previews and Python allocations run the same fixtures.

Per-bill/payment amount bound: 1_000_000_000paise. Aggregate balances may exceed a single bill. Auth user IDs are Django integers serialized to string for client ownership keys. Sign-in uses the four-digit email-code endpoints below. Successful native confirmation returns allauth `meta.session_token` and `data.user.id`; use the stringified user ID. Existing valid sessions remain usable. Password login, signup, reset and reauthentication cannot bypass email codes.

## Phase4 operations

- GET `/me` gives current Django user plus their payment profile; PUT `/me/payment-profile` body `{vpa}` changes only the caller's own VPA/version.
- POST `/groups/{id}/invites` body `{command_id,participant_id}` returns write ack plus `token` and `url`; only organizer; share is manual. Token scopes a read view to that participant.
- GET `/invites/{token}` requires no login and returns that participant's balance, involved records and counterparties only. POST `/invites/{token}/claim` body `{command_id}` needs authenticated native session-token or same-origin browser-session access; browser mutation requires CSRF. Manual share-link claims require explicit organizer approval. Email-bound invitations require the exact intended, OTP-verified address and then link that participant directly. The generated `/invite/{token}` URL redirects into the same Expo web app.
- POST `/groups/{id}/invites/{invite_id}/approve` or `/revoke` body `{command_id}`. Approval links exact pending claimant and participant; never matches name/email. Owner sees claimant account identity before approving.
- POST `/groups/{id}/opening-balances` creates a pending vector. POST `/groups/{id}/opening-balances/{opening_id}/acknowledge` body `{command_id}` acknowledges caller's claimed participant. It affects balances only after every nonzero participant acknowledges. Snapshot includes `opening_balance` with `accepted` and `acknowledgments`.
- POST `/groups/{id}/payment-attempts` body `{command_id,id,sender,recipient,amount,group_version,payee_version}`. Only signed-in sender; recipient must be linked with a current payment profile. Amount limited to the current simplified transfer. An existing active same-pair attempt is reused rather than duplicated. Write response remains `{id:group_id,version}`; fetch the accepted snapshot to select the actual active attempt ID. Snapshot `payment_attempts` preserves quoted amount and exposes linked `settlement_id`/`recorded_amount` when present.
- POST `/groups/{id}/payment-attempts/{attempt_id}/report`, `/confirm`, `/cancel` body `{command_id}`. Report is payer assertion only. Confirm is receiver-only and posts exactly one settlement; later acknowledgment of a manual record changes provenance only. Cancel permitted only before a payer report and never erases a report. No callback endpoint marks bank payment successful.
- GET `/groups/{id}/payment-attempts/{attempt_id}/launch` checks sender, group/profile revisions and quote expiry; returns VPA, exact paise amount, recipient, note, `currency:INR`, `expires_at`, `group_version`, `bank_verified:false` and `direct_launch_supported:true`. Supported clients build an encoded UPI URL only after validating these details. iOS independently probes Google Pay, PhonePe, Paytm, CRED, BHIM, Amazon Pay and a generic UPI handler, using the supplied QRScanner routes and its query allowlist. Only detected handlers are offered. Except for the documented Google Pay route, these are reference candidates without physical/provider certification. Generic iOS UPI does not enumerate all brands. Android uses the OS resolver. WhatsApp has no named route; see [.dev/UPI_SUPPORT.md](.dev/UPI_SUPPORT.md). Web offers a QR and copyable details. Opening, cancelling or returning never posts a settlement or payer report. Real bank-payment execution remains unverified. An expired quote never discards a reported payment.
- POST `/groups/{id}/archive` body `{command_id,archived}` owner-only.
- GET `/account/export` includes caller's accepted groups; DELETE `/account` deactivates login, removes credentials/contact/payment profile, anonymizes retained shared ledger attribution and preserves other members' financial history.

Snapshot `invites` is visible to the organizer only. It includes claimant identity for manual approval and intended-email/send-state metadata for explicit email invitations. A typed contact email does not establish identity. Email-bound public reads reveal no ledger before the exact intended address is verified; forwarded, revoked, expired or mismatched invitations cannot grant access. Creating a person or editing their email sends nothing.

POST `/groups/{id}/participants` body `{command_id,id,name}` adds an unclaimed participant, organizer-only, cap100. Existing expense allocations remain unchanged and new participant starts withzero historical share. Snapshot `totals` provides accepted gross purchase spending plus each participant paid/share totals, allpaise strings. Repayments and opening balances do not count as purchase spending.

## Splitwise CSV import

- POST `/imports/splitwise/preview` with `{csv}` returns `{source_hash,currency,members,expense_count,payment_count,balances,unresolved,warnings,duplicate_group}`. Balances and unresolved `amount` use string paise. Unresolved rows include their physical CSV start-line number; member indexes follow the CSV header. Preview writes nothing.
- POST `/imports/splitwise` with `{command_id,id,csv,name,self_index,payers}` creates one new shared group atomically. `payers` maps unresolved row-number strings to zero-based member indexes. Only `self_index` is linked to the caller. Result `{id,version,already_imported}` identifies either the new group or the caller's existing import. Same-command retries preserve payload identity; semantic source duplicates cannot post twice.
- INR exports are supported up to 1 MiB, 10,000 transactions and 100 members. Historical Payment rows become settlement records. The Total balance footer is verified and excluded. CSV nets are reconstructed into one payer and exact shares; original contribution details, comments and receipts are unavailable. Balance-neutral bills require a payer choice; ambiguous multiple-positive-net bills and unsupported currencies are rejected.

## Private photos and bill attachments

All file routes require normal account authentication. File metadata is `{id,name,content_type,size}`, where size is the optimized artifact's byte count. No R2 credentials, object keys or signed URLs appear in snapshots or persisted client metadata.

- GET `/me` includes `avatar:metadata|null`. POST `/me/avatar` accepts multipart `id` (client UUID) and `file`, returning `{avatar,cleanup_pending}`. DELETE `/me/avatar` returns `{removed:true,cleanup_pending}`. Photo access is limited to its owner.
- GET `/groups/{group_id}/expenses/{expense_id}/attachments` returns `{attachments,can_modify}`. POST the same path accepts multipart `id` and `file`, returning `{attachment,version}`. DELETE `.../attachments/{file_id}` returns `{removed:true,cleanup_pending,version}`. Current linked members may read. Archived groups are read-only; deleted bills cannot be read or changed. Media changes increment Group.version, preserving Expense.version and all financial amounts.
- GET `/media/{file_id}/url` rechecks ownership/group access and returns `{url,expires_at}` for a private signed GET valid for five minutes. Removal denies new URLs immediately; an already issued URL may work until expiry. URLs are transient and must not be saved in SQLite or exports.
- Uploads use a client UUID and original-byte fingerprint. Retrying the same file returns its accepted metadata without duplicate history; a changed file with that ID returns 409. Removed IDs cannot resurrect. Removal hides metadata before deleting the object; `cleanup_pending:true` means logical removal succeeded and repeated DELETE can retry cleanup. A concurrent file change returns a retryable 409.

Only processed artifacts reach R2 under `avatars/` or `bills/`; raw inputs are temporary and closed on every outcome. JPEG, PNG and WebP inputs are oriented, stripped of metadata and converted to full-color JPEG at quality 82. Avatars accept up to 5 MiB and become at most 512 pixels on their long edge; bill images accept up to 20 MiB and become at most 2400 pixels. Convert iPhone HEIC to JPEG through the native picker. Bills support at most 10 attachments.

Bill PDFs accept up to 20 MiB and 100 pages. pypdf rewrites structure, compresses content streams and deduplicates objects while preserving searchable text. Encrypted, signed, active/interactive, embedded-file, malformed and excessive-resource PDFs are rejected explicitly. Already compressed PDFs may not shrink. JSON group/account exports include attachment metadata and the account's photo metadata; CSV exports retain financial rows only.

Configure backend-only `R2_BUCKET`, `R2_ENDPOINT_URL`, `R2_REGION`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`. Run migrations 0004 and 0005 before serving this release. `python manage.py purge_media` manually retries up to 100 retired object deletions and abandons interrupted pending uploads older than one day. It skips active/in-progress files; run it again when its summary reports pending cleanup. There is no scheduler or worker.

## Canonical account app follow-up

`POST /groups/{group_id}/participants/{participant_id}/remove` accepts `{command_id}` and returns the usual idempotent write result. Only the group owner can remove a different participant. A nonzero balance, unresolved reported payment or pending nonzero opening balance blocks removal with HTTP409. The participant is marked removed; historical amounts/splits remain, membership access and invitations are revoked, queued push delivery is skipped, and a direct ledger is archived. Financial writes cannot reopen removed debt or alter a removed person's historical paid/share amounts. Snapshots retain removed participants with `removed:true`; group indexes and authorization require active membership.

For new settlement writes, omitted `date` means today. Explicit `date:null` preserves an unknown earlier date. Snapshots retain null and CSV exports leave it blank. Older persisted command receipts still replay without changing their fingerprint.

Mobile sync is automatic. The SQLite account/backend key owns cache, drafts and ordered outbox commands; logout does not delete them. After a successful index plus every listed snapshot, revoked caches are hidden while unsent work remains exportable. A partial read never prunes. Older unowned phone data requires explicit account and participant selection. Recovery preserves original financial IDs, deleted/reversed state and original history in account-scoped recovery records; divergent server copies are not silently overwritten. No generalized server history import endpoint was added.

## Email codes and direct-person invitations

- POST `/_allauth/{app|browser}/v1/auth/code/request` `{email}` returns `{data:{challenge_id,expires_in:180,retry_after:60}}`, with generic validation/rate/delivery errors. Existing and new addresses follow the same flow. Native clients retain any pre-auth session token only in memory.
- POST `.../auth/code/confirm` `{challenge_id,code}` accepts exactly four ASCII digits, including leading zero. Success creates or restores the existing allauth identity and native token or HttpOnly browser session cookie. Codes expire after three minutes and are single use. Only a keyed digest is stored. PostgreSQL locks enforce three attempts and shared email/network quotas across workers; resending cannot reset the short-window attempt budget. No raw code belongs in sessions, database rows, logs or API responses.
- POST `/groups/{group_id}/participants/{participant_id}/contact` `{command_id,email}` changes delivery metadata for the organizer's unclaimed other person in a two-person direct ledger and revokes stale email invitations.
- POST `.../email-invite` `{command_id}` explicitly sends the invitation and returns `{id,version,invite:{id,state,sent_at,retry_after}}`. The invite ID is the send command ID; retry the same immutable command after a transient/uncertain failure. Failed delivery retains the person and ledger. Resend is bounded and idempotent.
- Server environment: `RESEND_API_KEY`, `DEFAULT_FROM_EMAIL=MeroSplit <mail@merosplit.com>`, `EMAIL_REPLY_TO=mail@merosplit.com`, `PUBLIC_WEB_URL=https://api-production-fb6ac.up.railway.app`. No provider key is sent to native or web clients. Publisher owns actual runtime configuration and live inbox acceptance.

## Shared web app

The same Expo screens run under `/app/`; root redirects there. API, allauth, legal and private-media routes take precedence. Browser mutations use same-origin HttpOnly sessions plus CSRF and an expected account ID. A stale tab cannot replay its account's queue with another account's cookies. Browser SQLite owns the same account-scoped drafts/cache/outbox. The service worker caches application assets only, never API responses or private media. Private images/PDFs use an authorized same-origin streaming route. Browser push is explicitly unavailable. Run `pnpm export:web` before building the API deployment context, and preserve the emitted worker/WASM assets and isolation headers.

## Bounded history contract

- GET `/groups/{id}/summary?limit=50` returns `read_mode:summary`, complete server-computed balances/transfers/totals/participants/opening state, and at most50 bills, payment records, activity entries and actionable payment attempts. The maximum page size is100. Owner invitations are limited to the latest current invite per person, at most100.
- `history:{bills,activity,settlements,attempts}` supplies each `next_cursor`. GET `/groups/{id}/history/{resource}?limit=50&version=N&cursor=...` returns `{read_mode:page,group_id,version,items,next_cursor}`. Bill filters are `deleted=all|active|deleted` and `q` across title/notes; payment records accept `reversed=all|active|reversed`; activity accepts `kind`; attempts accept `sender`, `recipient`, `state=active|all`. An expired prepared attempt remains available for explicit cancellation.
- Signed cursors bind account, group, resource, filters, page size and group version. A changed version returns409 and resets the browsing pages from a fresh summary. Access is independently checked after the group lock on every request.
- GET `/groups/{id}/expenses/{expense_id}?version=N` returns one complete authorized bill, including a deleted bill for restoration, plus `read_mode:detail`, `group_id`, `group_version`.
- Browsing snapshots live in SQLite `group_summaries`; complete legacy/recovery snapshots keep their existing storage contract. A newer accepted version invalidates older cached history and the single focused bill detail, including text redacted after account deletion. Page controls replace their50 rows instead of mounting an accumulating history. Only downloaded pages and the last focused older bill are available offline.
- Outbox `base_version` is local metadata, never sent as part of an immutable API command. Summary-mode pending balance previews require that known starting version to equal the current accepted version. A lost response followed by a newer summary therefore cannot count an accepted bill or payment twice. Old commands with no baseline remain queued but cannot invent a pending total.

An isolated synthetic test with10,000 bills, changes, payment records and attempts measured163,434 raw summary bytes versus54,331,251 full snapshot bytes with14 queries. This is a local correctness/payload fixture, not a production throughput or latency guarantee. Financial calculation still scans all monetary source rows; no denormalized balance table or new infrastructure was added.


## Optional private store-review access

`STORE_REVIEW_AUTH_JSON` defaults to an empty list. An explicitly configured exact existing active nonstaff synthetic ID/email can use its server-hashed four-digit demo credential with the ordinary request/confirm endpoints. The challenge still expires after180seconds, consumes once, and shares the same atomic three-attempt and mailbox/network limits. No email is sent, no new identity is created, and the mailbox is not marked verified. Other users retain delivered email OTP.

Configured identities can access only reviewer-owned groups with no linked real users. Authenticated group reads/writes, exports, media, claims/approvals and push enforce this separation; demo identities cannot send email invitations. Existing public manual invitation previews remain bearer capabilities. A blank hash disables demo login while preserving reservations. Removing an entry requires the publisher to invalidate existing sessions first. Private store Notes/provisioning and live native/web acceptance belong to the publisher; no raw credential or provider key belongs in the app or repository.
