# Functional contract

Base `/api/v1`. JSON uses integer strings for all paise and UUID strings for entity IDs. Currency INR only. Positive balance means owed to participant. Actor identity is Django/allauth session ownership. Native auth uses allauth app session tokens in `X-Session-Token`; no custom JWT/user store.

All mutating ledger requests contain `command_id` UUID. Bill edits and reversals also contain the current bill `version` integer. Replaying identical actor/command/payload returns the original result; changed payload returns409. Error JSON has `error` and `detail`.

- GET `/health`, `/ready` are unauthenticated liveness/database readiness.
- POST `/groups` body `{command_id, id, name, participants:[{id,name,email?}]}`. Creator is participant with their user ID linked explicitly by server. Client supplies their participant `id` as `self_participant_id`. A supplied email links an existing unambiguous active account only when its current address is already verified by allauth. Unknown/unverified addresses stay unlinked; no identity is created. Returns `{id:group_id,version,linked_participant_ids:[...]}`; fetch snapshot separately. The original linked-ID outcome is stored in the command receipt; replay never links a later-created identity.
- POST `/group-invite-links/preview` requires an authenticated account and a current group capability. It returns `{name,already_member,version,people:[{id,name}]}`. `people` contains all current nonremoved, account-unlinked, email-less group people without an active pending personal claimant. No partial choice list or new-member restriction is introduced. Public `/j/` previews remain name-only and never expose account emails, candidates or financial records.
- POST `/group-invite-links/join` `{command_id,token,participant_id?,preview_version?,display_name?}` joins as a new person when no target is supplied. An explicit existing-person claim requires the current preview version and the same current eligibility under actor/group/person locks. It updates that Participant in place, preserves all financial IDs/history and the organizer, and records one claim event. A new explicit claim from an already-linked account is409; exact command replay and legacy open-group requests retain their existing behavior. Optional trimmed `display_name` is a group-person label only, never an account name or group title. Migration0030 adds its blank-default override. Existing personal/addressed invite approval and verified-email policies remain unchanged.
- Authenticated full and summary group participants include `account_email`, the current active linked User email or null, for authorized group members. It is separate from organizer-only guest `email` contact destinations. Linked group display overrides precede the normal profile-name fallback; `recorded_name` stays intact. Older equal-version caches lacking account_email refresh once. No account emails are added to public invitation/candidate responses.
- Optional `is_direct:true` creates a friend ledger with exactly two participants; adding a third is rejected. The default is false. Group lists, snapshots and JSON exports preserve the flag. Omitted and explicit false retain legacy command-replay compatibility.
- GET `/groups` returns the complete authorized index `{groups:[{id,name,version,archived,is_direct,hidden}]}`. `hidden` is private to the caller; archived and hidden groups remain in this index.
- GET `/groups/{id}` returns `{id,name,version,participants:[{id,name,user_id}],expenses:[...],settlements:[...],balances:{participant_id:paise},transfers:[{sender,recipient,amount}],activity:[...]}`. The complete authorized index supplies versions. Refresh reuses complete same-version snapshots for this account/backend and fetches only missing or changed groups before reconciling access. The updated client requests bounded summaries and history pages. The legacy full snapshot remains available for older clients, exports and explicit recovery; bounded data is stored separately and never presented as a complete history.
- POST `/groups/{id}/expenses` body `{command_id,id,description,total,paid:{id:paise},split:{mode:'equal'|'exact'|'percent'|'shares',values:{id:decimal_string}},date:'YYYY-MM-DD',category,notes}`. Equal values are selected participant IDs with value'1'. Percent values total100.00; shares max4decimal places. Returns `{id:group_id,version}`; fetch snapshot separately.
- PUT `/groups/{id}/expenses/{id}` same body plus `version` of expense. POST `/groups/{id}/expenses/{id}/reverse` takes `{command_id,version}` and appends a linked `expense_reversed` Change with the original accepted values. The original bill stays stored; `deleted` is the legacy balance-exclusion flag. Saved bill DELETE and restore routes are unavailable. Expense output includes `id,version,description,total,paid,shares,split,date,category,notes,deleted`.
- POST `/groups/{id}/settlements` body `{command_id,id,sender,recipient,amount,attempt_id?,date?,expected_group_version?}` creates explicit manual bookkeeping. For a payment-return confirmation, pass the frozen exact attempt, amount and quote group version. Under the group lock it requires that version, a prepared payer-owned attempt and the unchanged recipient UPI profile; a changed balance/payee returns409 without writing. Quote expiry alone does not prevent recording an actual payment. Replay the same command and body after uncertainty: its original receipt returns before these freshness checks. Omitting `expected_group_version` preserves existing manual bookkeeping, including partial amounts. POST `/settlements/{id}/reverse` body `{command_id}`.
- POST `/groups/{id}/opening-balances` body `{command_id,id,balances:{id:paise},source,cutoff}` creates a pending balanced opening proposal. It posts only after every nonzero linked participant acknowledges.
- GET `/groups/{id}/export?format=json|csv` returns accepted records with allocations and provenance.
- Individual bill details add `added_by`, payment details add `recorded_by_name`, and linked reversal details add `actor_name`. These are authorized display labels from the actual creator/recorder/reversal event, never from payer direction. Missing, anonymized or imported original actors return null. List and accepted export projections keep their existing fields.

Payment attempts, invites/claiming, account export/deletion and group archive have the explicit endpoints below. The mobile client uses plain fetch and persists queued commands; no generated SDK or generic command bus. The Python API is authoritative; TypeScript previews and Python allocations run the same fixtures.

Per-bill/payment amount bound: 1_000_000_000paise. Aggregate balances may exceed a single bill. Auth user IDs are Django integers serialized to string for client ownership keys. Sign-in uses the email-link and four-digit fallback endpoints below. Successful native confirmation returns allauth `meta.session_token` and `data.user.id`; use the stringified user ID. Existing valid sessions remain usable. Password login, signup, reset and reauthentication cannot bypass email codes.

## Native Sign in with Apple

- iOS uses the official `expo-apple-authentication` button. POST `/_allauth/app/v1/auth/apple/challenge` with `{process:"login"|"connect"}` returns a session-bound nonce/state and 180-second lifetime. POST `.../apple/token` requires `process,id_token,authorization_code,state`; optional initial-only `given_name,family_name` are display data. No browser/Android Apple route or redirect is added.
- Pinned allauth verifies Apple's signature, issuer and bundle audience; server also checks expiry, subject, nonce/state, actor/process and the one-use fence. One code exchange verifies the same subject. Allauth remains the only user/session owner. Email collisions require email login then explicit connect in Me. Returning subjects retain their existing user, including private-relay identities without fresh name/email.
- Server-only `APPLE_SIGN_IN_PRIVATE_KEY` and stable `APPLE_SIGN_IN_TOKEN_ENCRYPTION_KEY` never enter web/native bundles. Only the encrypted refresh credential is retained in existing allauth `SocialToken`; no raw identity/access/refresh token is saved in user/profile/session data. Public configuration names are in `apps/api/.env.example`. No new database migration.
- Existing confirmed DELETE `/api/v1/account` captures encrypted Apple credentials before auth cascade and attempts one bounded revocation after commit. It returns `apple_revocation:"revoked"` only after Apple confirms; missing credentials or failure returns `"manual_required"` and the client instructs manual removal in Apple Account. Account deletion and existing financial-history retention still complete. Ordinary signout does not revoke the Apple grant. No standalone disconnect or new deletion workflow is added.
- Root must enable the App ID capability, provide a compatible profile using the existing signer and configure the server before live use. Existing binaries lack this new module; a separately approved current native build and real-device/provider QA are required. Source/mock tests do not prove live sign-in or App Review acceptance.

## Phase4 operations

- GET `/me` gives current Django user, `display_name` and payment profile. PUT `/me/profile` `{display_name,only_if_unnamed?:boolean}` trims and requires 1–120 characters, returning `{display_name}`; it preserves login/email identity and existing sessions. Name-only onboarding sends strict boolean `only_if_unnamed:true`: under the existing user lock an established name wins without a revision; ordinary profile edits omit it. A changed name advances each active linked group's version; repeating the same trimmed name is a no-op. Full and summary participant output uses the active linked account's nonblank display name, falling back to its stored label, and always includes `recorded_name` with that original label. Removed/unlinked names, group titles, financial allocations and historical records stay intact. Clients must fetch old cached groups once if `recorded_name` is absent, even when their version matches. PUT `/me/payment-profile` body `{vpa}` changes only the caller's own VPA/version.
- POST `/groups/{id}/invites` body `{command_id,participant_id}` returns write ack plus `token` and `url`; only organizer; share is manual. Token scopes a read view to that participant.
- GET `/invites/{token}` requires no login and returns that participant's balance, involved records and counterparties only. POST `/invites/{token}/claim` body `{command_id}` needs authenticated native session-token or same-origin browser-session access; browser mutation requires CSRF. Manual share-link claims require explicit organizer approval. Email-bound invitations require the exact intended, verified address and then link that participant directly. The generated `/invite/{token}` URL redirects into the same Expo web app.
- POST `/groups/{id}/invites/{invite_id}/approve` or `/revoke` body `{command_id}`. Approval links exact pending claimant and participant; never matches name/email. Owner sees claimant account identity before approving.
- POST `/groups/{id}/opening-balances` creates a pending vector. POST `/groups/{id}/opening-balances/{opening_id}/acknowledge` body `{command_id}` acknowledges caller's claimed participant. It affects balances only after every nonzero participant acknowledges. Snapshot includes `opening_balance` with `accepted` and `acknowledgments`.
- POST `/groups/{id}/payment-attempts` body `{command_id,id,sender,recipient,amount,group_version,payee_version}`. Only signed-in sender; recipient must be linked with a current payment profile. Amount limited to the current simplified transfer. An existing active same-pair attempt is reused rather than duplicated. Write response remains `{id:group_id,version}`; fetch the accepted snapshot to select the actual active attempt ID. Snapshot `payment_attempts` preserves quoted amount and exposes linked `settlement_id`/`recorded_amount` when present.
- POST `/groups/{id}/payment-attempts/{attempt_id}/report`, `/confirm`, `/cancel` body `{command_id}`. Report is payer assertion only. Confirm is receiver-only and posts exactly one settlement; later acknowledgment of a manual record changes provenance only. Cancel permitted only before a payer report and never erases a report. No callback endpoint marks bank payment successful.
- GET `/groups/{id}/payment-attempts/{attempt_id}/launch` checks sender, group/profile revisions and quote expiry; returns VPA, exact paise amount, recipient, note, `currency:INR`, `expires_at`, `group_version`, `bank_verified:false` and `direct_launch_supported:true`. Supported clients build an encoded UPI URL only after validating these details. iOS independently probes Google Pay, PhonePe, Paytm, CRED, BHIM, Amazon Pay and a generic UPI handler, using the supplied QRScanner routes and its query allowlist. Only detected handlers are offered. Except for the documented Google Pay route, these are reference candidates without physical/provider certification. Generic iOS UPI does not enumerate all brands. Android uses the OS resolver. WhatsApp has no named route; see [.dev/UPI_SUPPORT.md](.dev/UPI_SUPPORT.md). Web offers a QR and copyable details. Opening, cancelling or returning never posts a settlement or payer report. Real bank-payment execution remains unverified. An expired quote never discards a reported payment.
- POST `/groups/{id}/archive` body `{command_id,archived}` owner-only.
- GET `/account/export` includes caller's accepted groups; DELETE `/account` requires `{confirmation:"delete",email:"current account email"}`. The exact confirmation word and case-insensitive trimmed current email are checked under the user lock before any destructive work. It deactivates login, removes credentials/contact/payment profile, anonymizes retained shared ledger attribution and preserves other members' financial history.

Snapshot `invites` is visible to the organizer only. It includes claimant identity for manual approval and intended-email/send-state metadata for explicit email invitations. Email-bound public reads reveal no ledger before exact intended-address verification. A manual invitation token cannot authenticate; revoked, expired or mismatched invitations cannot grant membership. An email sign-in proof is a bearer credential for its intended account, including if forwarded. Contact editing alone never sends or grants membership. Explicitly adding an already verified account grants ordinary group access and queues eligible membership notifications; adding an unknown address sends no invitation.

POST `/groups/{id}/participants` body `{command_id,id,name,email?}` adds a participant, organizer-only, cap100. That person is immediately usable in new bills; existing expense allocations remain unchanged and the new participant starts with zero historical share. A unique active account with that verified current address links immediately and sees the ledger on its dashboard; other addresses remain unlinked for explicit invitation. Existing/removed account duplicates and conflicting identities are rejected. Direct People ledgers retain their two-person limit. Returns the usual write result plus `linked_participant_ids`. Snapshot `totals` provides accepted gross purchase spending plus each participant paid/share totals, allpaise strings. Repayments and opening balances do not count as purchase spending.

## Splitwise CSV import

- POST `/imports/splitwise/preview` with `{csv}` returns `{source_hash,currency,members,expense_count,payment_count,balances,unresolved,warnings,duplicate_group}`. Balances and unresolved `amount` use string paise. Unresolved rows include their physical CSV start-line number; member indexes follow the CSV header. Preview writes nothing.
- POST `/imports/splitwise` with `{command_id,id,csv,name,self_index,payers}` creates one new shared group atomically. `payers` maps unresolved row-number strings to zero-based member indexes. Only `self_index` is linked to the caller. Result `{id,version,already_imported}` identifies either the new group or the caller's existing import. Same-command retries preserve payload identity; semantic source duplicates cannot post twice.
- INR exports are supported up to 1 MiB, 10,000 transactions and 100 members. Historical Payment rows become settlement records. The Total balance footer is verified and excluded. CSV nets are reconstructed into one payer and exact shares; original contribution details, comments and receipts are unavailable. Balance-neutral bills require a payer choice; ambiguous multiple-positive-net bills and unsupported currencies are rejected.

## Private photos and bill attachments

All file routes require normal account authentication. File metadata is `{id,name,content_type,size}`, where size is the optimized artifact's byte count. No R2 credentials, object keys or signed URLs appear in snapshots or persisted client metadata.

- GET `/me` includes `avatar:metadata|null`. POST `/me/avatar` accepts multipart `id` (client UUID) and `file`, returning `{avatar,cleanup_pending}`. DELETE `/me/avatar` returns `{removed:true,cleanup_pending}`. Photo access is limited to its owner.
- GET `/groups/{group_id}/expenses/{expense_id}/attachments` returns `{attachments,can_modify}`. POST the same path accepts multipart `id` and `file`, returning `{attachment,version}`. DELETE `.../attachments/{file_id}` returns `{removed:true,cleanup_pending,version}`. Current linked members may read. Archived groups are read-only; reversed bills cannot be read or changed. Media changes increment Group.version, preserving Expense.version and all financial amounts.
- GET `/media/{file_id}/url` rechecks ownership/group access and returns `{url,expires_at}` for a private signed GET valid for five minutes. Removal denies new URLs immediately; an already issued URL may work until expiry. URLs are transient and must not be saved in SQLite or exports.
- GET `/media/{file_id}/thumbnail` rechecks the same access for PDFs and returns `{data_url}`, a JPEG of the first page with a maximum 224-pixel edge and 64 KiB output. Success and preview errors use `private, no-store`. Each API worker admits one short-lived renderer, waits at most 250 ms for admission and kills/reaps it after a 5-second render deadline. Linux children have explicit memory/CPU/file limits. Anonymous temporary output closes on every exit; no R2 preview object or ledger write is created. A failed preview can be retried; opening the full file still uses `/url`.
- Uploads use a client UUID and original-byte fingerprint. Retrying the same file returns its accepted metadata without duplicate history; a changed file with that ID returns 409. Removed IDs cannot resurrect. Removal hides metadata before deleting the object; `cleanup_pending:true` means logical removal succeeded and repeated DELETE can retry cleanup. A concurrent file change returns a retryable 409.

Only processed artifacts reach R2 under `avatars/` or `bills/`; raw inputs are temporary and closed on every outcome. JPEG, PNG and WebP inputs are oriented, stripped of metadata and converted to full-color JPEG at quality 82. Avatars accept up to 5 MiB and become at most 512 pixels on their long edge; bill images accept up to 20 MiB and become at most 2400 pixels. Convert iPhone HEIC to JPEG through the native picker. Bills support at most 10 attachments.

Bill PDFs accept up to 20 MiB and 100 pages. pypdf rewrites structure, compresses content streams and deduplicates objects while preserving searchable text. Encrypted, signed, active/interactive, embedded-file, malformed and excessive-resource PDFs are rejected explicitly. Already compressed PDFs may not shrink. JSON group/account exports include attachment metadata and the account's photo metadata; CSV exports retain financial rows only.

Configure backend-only `R2_BUCKET`, `R2_ENDPOINT_URL`, `R2_REGION`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`. Run migrations 0004 and 0005 before serving this release. `python manage.py purge_media` manually retries up to 100 retired object deletions and abandons interrupted pending uploads older than one day. It skips active/in-progress files; run it again when its summary reports pending cleanup. Media cleanup is an explicit command; the existing notification worker does not schedule it.

## Canonical account app follow-up

`POST /groups/{group_id}/participants/{participant_id}/remove` accepts `{command_id}` and returns the usual idempotent write result. Only the group owner can remove a different participant. A nonzero balance, unresolved reported payment or pending nonzero opening balance blocks removal with HTTP409. The participant is marked removed; historical amounts/splits remain, membership access and invitations are revoked, queued push delivery is skipped, and a direct ledger is archived. Financial writes cannot reopen removed debt or alter a removed person's historical paid/share amounts. Snapshots retain removed participants with `removed:true`; group indexes and authorization require active membership.

For new settlement writes, omitted `date` means today. Explicit `date:null` preserves an unknown earlier date. Snapshots retain null and CSV exports leave it blank. Older persisted command receipts still replay without changing their fingerprint.

Mobile sync is automatic. The SQLite account/backend key owns cache, drafts and ordered outbox commands; logout does not delete them. After a successful index plus every listed snapshot, revoked caches are hidden while unsent work remains exportable. A partial read never prunes. Older unowned phone data requires explicit account and participant selection. Recovery preserves original financial IDs, deleted/reversed state and original history in account-scoped recovery records; divergent server copies are not silently overwritten. No generalized server history import endpoint was added.

## Email codes and participant invitations

- POST `/_allauth/{browser|app}/v1/auth/link/request` `{email,email_reminders_disclosed?:boolean}` sends one frozen sign-in email with a primary link and four-digit fallback, returning `{data:{challenge_id,expires_in:180,retry_after:60,accepted:true}}` only after provider acceptance. The existing public challenge pointer lets “Use a code instead” immediately confirm the already-delivered fallback without another request or cooldown. No raw code/proof is returned. The strict disclosure flag is stored on the login grant: the legacy field remains proof-bound for compatibility, but never enables a channel; new identities start email off and existing preferences are unchanged. Ordinary `code/request` remains available. The same proof contract serves web and native clients; installed-native acceptance remains a separate publisher gate.
- Email entry is `/app/sign-in/{grant_id}#proof=...`. GET/HEAD only serve the shell, with no account creation or redemption. A visible browser scrubs the fragment before assets. POST `.../auth/link/inspect` `{grant_id,proof}` checks the bearer without writes and returns `data:{email,user_id,purpose,current_user_id,current_email}`. A different authenticated account requires a popup naming both emails before POST `.../auth/link/exchange` `{grant_id,proof,switch_from_user_id?:number,email_reminders_disclosed?:boolean}` with same-origin CSRF. A supplied switch ID must match the current authenticated account; a missing, signed-out or rebound account is rejected before redemption. Cancel discards only ephemeral link state and preserves the mounted form, account cache and unsent work. The exchange flag cannot elevate an undisclosed grant. Success uses the normal allauth envelope/session and adds `data.target:{kind:'home'}|{kind:'group',group_id}` and `data.needs_name:boolean`. The server supplies the closed target; no redirect input is accepted. A valid explicit invitation initializes only an unnamed account from its supplied name, redeems only that exact invitation, and preserves established names.
- POST `.../auth/link/resume` `{grant_id}` reconciles a correct already-authenticated session after a lost response or consumed/expired proof, rechecking current target access without minting another session or claim. POST `.../auth/link/renew` `{grant_id}` needs no email/code input and sends only to the stored recipient, with the same `{retry_after:60,accepted}` data. Missing/unusable selectors return accepted false, not a delivery claim. Invalid/expired/revoked/used proof errors are generic400 `email_link_unavailable`; quotas429 and uncertain provider delivery503 never mean sent. Recovery cannot resurrect a deleted invitation or identity. A revoked/expired invitation can recover an existing recipient's home account without joining the ledger.
- Login proof lasts180 seconds; invitation proof never outlives its exact seven-day invitation; digest proof starts at first eligible provider attempt and lasts24 hours. PostgreSQL locks and shared OTP email/network budgets enforce atomic single consume, including races between a link and its fallback code. Wrong-account exchange flushes the old Django session/device bindings before normal allauth login; clients retain account-scoped drafts and stop old sync first. Correct-session reopening requires current authorization. Store-demo identities cannot use email-link authentication.
- Proofs are purpose-separated HMACs bound to immutable selector/recipient/issued-user/purpose/target/origin/expiry/disclosure metadata. Rows store only a digest, frozen nonsecret template payload and placeholders. Actual URL/code/expiry materialize only at the existing email boundary; retries keep the same body/key even after template/origin changes. An uncertain recovery send retries its same replacement; no automatic new credential/key after the23-hour provider window. Account deletion purges matching proof rows, and exact invitation deletion cascades its unbound proofs. Neither raw proof nor fallback code belongs in sessions/database/logs. Ordinary HTTP mail scanners are inert; a scanner executing the same visible JavaScript can redeem a bearer link and cannot be universally distinguished without interaction.
- POST `/_allauth/{app|browser}/v1/auth/code/request` `{email,email_reminders_disclosed?:boolean}` returns `{data:{challenge_id,expires_in:180,retry_after:60}}`, with generic validation/rate/delivery errors. The optional disclosure defaults to false and accepts JSON booleans only, validated before issuing a challenge or sending email. The delivered link freezes this legacy metadata; neither code nor link sign-in enables email. Existing choices and reserved reviewer identities remain unchanged. Existing and new addresses follow the same flow. Native clients retain any pre-auth session token only in memory.
- POST `.../auth/code/confirm` `{challenge_id,code,email_reminders_disclosed?:boolean}` accepts exactly four ASCII digits, including leading zero. The optional flag defaults to false and accepts JSON booleans only; malformed values return the generic invalid response without consuming the code. Even a legacy true flag leaves new ordinary identities email off. Email is enabled only through the explicit notification preference action. Existing identity preferences and demo identities are unchanged. Success creates or restores the existing allauth identity and native token or HttpOnly browser session cookie. Codes expire after three minutes and are single use. Only a keyed digest is stored. PostgreSQL locks enforce three attempts and shared email/network quotas across workers; resending cannot reset the short-window attempt budget. No raw code belongs in sessions, database rows, logs or API responses.
- POST `/groups/{group_id}/participants/{participant_id}/contact` `{command_id,email}` changes delivery metadata for the organizer's active unclaimed participant in a group or direct People ledger. A changed email revokes every unapproved invitation, including older manual links. A saved-email participant requires explicit email invitation: new manual-share creation and old manual claim/approval are rejected. Name-only participants retain manual share and organizer approval.
- POST `.../email-invite` `{command_id}` explicitly links an existing verified active recipient, returning `{id,version,linked_participant_ids:[participant_id]}` without creating an invitation. Otherwise it sends the invitation and returns `{id,version,linked_participant_ids:[],invite:{id,state,sent_at,retry_after}}`. The invite ID is the send command ID; retry the same immutable command after a confirmed transient rejection. Its recorded unlinked outcome never becomes an implicit link on replay. Uncertain Cloudflare sends are held for reconciliation without another provider POST. Failed delivery retains the person and ledger; legacy frozen Resend sends keep their bounded idempotent retry behavior. The UI labels the action Send/Sending; server cooldown and receipt safety still apply.
- Server environment for new mail: `EMAIL_PROVIDER=cloudflare`, `CLOUDFLARE_EMAIL_ACCOUNT_ID`, `CLOUDFLARE_EMAIL_API_TOKEN`, `DEFAULT_FROM_EMAIL=MeroSplit <mail@merosplit.com>`, `EMAIL_REPLY_TO=mail@merosplit.com`, `PUBLIC_WEB_URL=https://merosplit.com`. Retain `RESEND_API_KEY` for already-frozen legacy sends. No provider key is sent to native or web clients. The publisher activates Cloudflare only after migration and a compatible API/worker rollout. Incoming mail@merosplit.com forwards through the existing incoming Cloudflare Worker to its verified destination stored in the private FORWARD_TO secret. Live credentials and environment overrides are changed only by the publisher.

## Unread expense notifications

- GET/PUT `/me/notifications/preferences` returns `{expense_updates:boolean,email_reminders:boolean,notifications_enabled:boolean,email_available:boolean,push_device_ids:UUID[]}`; PUT accepts only the two writable booleans. Raw master intent and channel choice are retained when master is muted; effective `notifications_enabled` additionally requires selected usable email or a current registered push route. The app excludes its own push route unless OS permission and registration are confirmed, and never requests permission while refreshing. Last-channel removal persists master off; re-registering never unmutes it. Legacy empty preferences display off without a write or implicit email opt-in. Failed saves retain confirmed settings. New accounts start email off, even legacy disclosure=true sign-ins. Activity/unread records remain independent; email opt-in applies only to subsequent ordinary bill creations.
- GET `/me/notifications?limit=50&expense_ids=comma-separated-UUIDs` returns `{notices:[{id,group_id,expense_id,expense_version,created_at}],has_more}`. Limit is 1–100. Optional bill scope accepts up to 50 IDs so an older visible page remains reachable beyond the global feed. Only current authorized, financially involved unread notices appear. Fetching never marks a notice seen.
- POST `/me/notifications/seen` `{notices:[{id,expense_version}]}` accepts up to 100 exact recipient IDs and returns `{seen:number}`. Send the actually rendered accepted bill revision: it must equal the current bill revision and cover the creation revision. Stale/future revisions, another account's IDs and duplicate acknowledgements do not mark unseen content. One device's acknowledgement suppresses unsent channels across devices.
- POST `/me/notifications/foreground` `{}` returns `{ok:true}` and records coarse explicit foreground engagement at most once per five minutes. Background fetches, hidden tabs, notification arrival/tap and unrelated requests must not call it or acknowledge unseen bills. These account operations use value/ID assignment, not financial command IDs.

Only ordinary new bills create recipient notices: positive canonical paid or share, linked active nonremoved account, excluding actor and configured reviewers. Payer net zero still qualifies. Bystanders, imports, edits/reversals, repayments and historical records do not create events. Contact-email events use the separate unclaimed notification contract below. Grace-time fanout checks current native bindings once after 30 seconds; later registration does not replay history. Identical foreground registrations refresh route freshness without changing binding revision. Routes older than 30 days or with expired/revoked sessions are ineligible. Generic push routing adds `notice_id` (also `event_id`) and the creation `expense_version`; provider acceptance is not OS display or seen state.

Linked-account email becomes eligible after 10 unread minutes, independently of foreground activity, installation or push delivery. It uses the current verified usable address and current account/mailbox preferences. Due notices coalesce into at most 100 per digest; an event is assigned at most once. There is no rolling daily recipient cap. Delete/archive/remove suppress unsent work; restore/unarchive does not replay cancelled creation events. Generic HTML/plaintext includes a purpose-bound sign-in link but no amounts, bill/group/person names or ledger access beyond the authenticated account's existing permissions.

Migrations 0011/0012 introduced the notice queues. Atomic migration 0016 marks historical notices and digests `email_policy=0`, disables historical email eligibility and cancels pending/sending legacy digests while preserving frozen payloads, assignments and held audit records. It then sets both Python and database defaults to1, so new inserts from an older API writer after migration belong to the current policy. The unique open digest is per recipient and policy, allowing a held generation0 audit record alongside generation1 work. This is a cutover without historical backfill. The existing `send_bill_notifications` worker also sends digests. Provider I/O stays outside transactions. ## Bounded history contract

- GET `/groups/{id}/summary?limit=50` returns `read_mode:summary`, complete server-computed balances/transfers/totals/participants/opening state, and at most50 mixed transactions, bills, payment records, activity entries and actionable payment attempts. The maximum page size is100. Owner invitations are limited to the latest current invite per person, at most100.
- `history:{transactions,bills,activity,settlements,attempts}` supplies each `next_cursor`. GET `/groups/{id}/history/{resource}?limit=50&version=N&cursor=...` returns `{read_mode:page,group_id,version,items,next_cursor}`. Bill filters are `deleted=all|active|deleted` and `q` across title/notes; payment records accept `reversed=all|active|reversed`; activity accepts `kind`; attempts accept `sender`, `recipient`, `state=active|all`. An expired prepared attempt remains available for explicit cancellation.
- `transactions` is one globally ordered canonical window, not a merge of separate pages. Rows are `{kind:'bill',date,bill:{id,version,description,total,paid,shares,date,category,deleted}}` or `{kind:'payment',date,payment:<settlement>}`. Known actual dates sort descending, payments precede bills on the same date, then IDs descend; unknown imported payment dates remain null and sort last. Reversed bills and payments retain their history flags. Bill/payment detail optionally includes a separate `reversal` record with event `id`, `sequence`, `created_at`, `kind`, `reversal_of` and an allowlisted `original` financial snapshot. Activity exposes a separate `bill_reversed` or `payment_reversed` event linked to the retained original. Reversal retries reuse the command receipt; an already reversed record cannot be reversed again. Payment reversal never transfers or refunds money. Optional `q` searches bill description/notes and excludes payments. Full bill details still use the exact bill endpoint.
- Signed cursors bind account, group, resource, filters, page size and group version. A changed version returns409 and resets the browsing pages from a fresh summary. Access is independently checked after the group lock on every request.
- GET `/groups/{id}/expenses/{expense_id}?version=N` returns one complete authorized bill, including a deleted bill for restoration, plus `read_mode:detail`, `group_id`, `group_version`.
- GET `/groups/{id}/settlements/{settlement_id}?version=N` returns one authorized settlement plus `read_mode:detail`, `group_id`, `group_version`. GET `/groups/{id}/payment-attempts/{attempt_id}?version=N` finds an exact attempt even when confirmed or outside the current page, returning IDs, amount/state, quoted `group_version`, `current_group_version`, expiry, linked settlement ID/amount and `settlement` or null; it does not expose historical UPI addresses. Both return409 for an explicitly stale version and404 after membership/scope revocation.
- GET `/activity?limit=50&cursor=...` returns `{read_mode:'activity',revision,items,next_cursor}` across currently authorized groups, ordered by event time and ID descending. Items have opaque `id`, `kind`, `created_at`, `group:{id,name}`, `actor:{name,is_self}|null` and an optional canonical `bill:{id,description,deleted}`, `payment:{id,sender:{id,name,is_self},recipient:{id,name,is_self},amount,reversed}`, or `person:{id,name,is_self}`. Kinds are `bill_added|bill_edited|bill_deleted|bill_restored|payment_recorded|payment_reversed|member_added|member_joined|member_removed|group_created|group_archived|group_unarchived`. Preparation, app opening, payer reports, cancellations, sync and provider events are excluded; later recipient acknowledgment does not invent another payment. Current labels/redaction apply, including stored labels for removed actors. A changed authorized group/version set invalidates the signed cursor with409. Neither Activity nor any history/detail/summary GET acknowledges a bill notice or records foreground engagement.
- Browsing snapshots live in SQLite `group_summaries`; complete legacy/recovery snapshots keep their existing storage contract. A newer accepted version invalidates older cached history and the single focused bill detail, including text redacted after account deletion. Page controls replace their50 rows instead of mounting an accumulating history. Only downloaded pages and the last focused older bill are available offline.
- Outbox `base_version` is local metadata, never sent as part of an immutable API command. Summary-mode pending balance previews require that known starting version to equal the current accepted version. A lost response followed by a newer summary therefore cannot count an accepted bill or payment twice. Old commands with no baseline remain queued but cannot invent a pending total.

An isolated synthetic test with10,000 bills, changes, payment records and attempts measured185,496 raw summary bytes versus54,331,317 full snapshot bytes with16 queries after adding the mixed window. Deep bill, dated/undated transaction and Activity keysets discarded no preceding rows in that fixture. This is local correctness/query-plan evidence, not a production throughput or latency guarantee. Financial calculation still scans all monetary source rows; no denormalized balance table or new infrastructure was added.
